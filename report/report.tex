\section{Data Choice, Objectives \& Success Metrics}

\boldparagraph{Why this data.} We use daily OHLCV history of the S\&P 500 index (Yahoo Finance, ticker \texttt{\^{}GSPC}, 2000--2026, 6{,}604 usable rows). The choice is deliberate for an \textit{MLOps} project rather than a pure modelling one: the data is free, clean, reliably available, and updates every trading day, so it realistically exercises ingestion, scheduling, and drift monitoring. It is also a genuine time series, which forces correct, leak-free engineering (chronological splits, time-aware validation and monitoring), and it is a \textit{low-signal} problem, exactly where solid operational tooling earns its value: small pipeline mistakes can masquerade as ``performance'', so contracts and tracking are essential.

\boldparagraph{What we try to achieve.} The task is binary classification: predict whether the next trading day closes higher than today, $y_t = \mathbb{1}[\text{Close}_{t+1} > \text{Close}_t]$. The real objective is to deliver a \textbf{production-grade ML lifecycle}: reproducible orchestration (Kedro), experiment tracking and a model registry (MLflow), data contracts (Great Expectations), drift monitoring (Evidently), explainability (SHAP), an offline feature store (Hopsworks), a served REST API (FastAPI + Docker), and automated tests (pytest). The model itself is intentionally simple so the engineering around it is the deliverable.

\boldparagraph{Success metrics.} We track success on two levels (Table~\ref{tab:success}). \textit{Model metrics} are Accuracy, Precision, Recall, F1, and ROC-AUC, with \textbf{ROC-AUC as the primary discrimination metric}. \textit{System (MLOps) metrics} define what ``done'' means operationally and are, for this PoC, the more important bar.

\section{System Architecture \& Data Quality}

The system is a directed acyclic graph of \textbf{Kedro} pipelines (Figure~\ref{fig:kedroviz}), each a set of nodes with declared inputs/outputs registered in a central data catalog, so every artifact is traceable to the node that produced it. A single \texttt{kedro run} executes the default end-to-end workflow: \texttt{data\_quality} $\rightarrow$ \texttt{cleaning} $\rightarrow$ \texttt{feat\_engineering} $\rightarrow$ \texttt{split} $\rightarrow$ \texttt{train} (+\,challenger) $\rightarrow$ \texttt{predict}. Three further pipelines run on demand: \texttt{data\_expectations} (contracts), \texttt{model\_explainability} (SHAP), and \texttt{data\_drift} (Evidently). Table~\ref{tab:stack} maps each MLOps concern to its tool. \textbf{Data quality} is enforced with Great Expectations at two checkpoints (raw OHLCV and engineered features); both pass fully (19/19 and 27/27), so a future data refresh that breaks an assumption fails loudly and early.

\section{Results: Data Exploration \& Modelling}

\boldparagraph{Exploration.} The index level is strongly trending and \textit{non-stationary}, while daily returns are stationary around zero with clustered volatility (Figure~\ref{fig:eda}); the target is mildly skewed toward up-days ($\approx53\%$). From price and volume we engineer eight leak-free features (returns, \texttt{sma\_10/20}, \texttt{sma\_ratio\_10}, \texttt{rsi\_14}, \texttt{volatility\_10}, \texttt{volume\_change}), kept small so every feature stays inspectable. The stationarity contrast directly explains the drift results in Section~\ref{sec:mlops}.

\begin{figure}[H]
    \centering
    \begin{subfigure}[t]{0.40\textwidth}\centering\includegraphics[width=\textwidth]{sp500_close_price.png}\caption{Close price (non-stationary).}\end{subfigure}\hspace{0.04\textwidth}
    \begin{subfigure}[t]{0.40\textwidth}\centering\includegraphics[width=\textwidth]{sp500_daily_returns.png}\caption{Daily returns (stationary).}\end{subfigure}
    \caption{Exploratory analysis. Trending levels vs.\ stationary returns motivate the feature-drift findings below.}
    \label{fig:eda}
\end{figure}

\boldparagraph{Modelling \& explainability.} A \textbf{champion} (\texttt{StandardScaler} + Logistic Regression) is compared with a \textbf{challenger} (Random Forest, 300 trees, depth 8, regularised), both under the identical chronological split with MLflow tracking. On the 992-row future test block (Table~\ref{tab:results}) the champion leads on Accuracy/Recall/F1 and is chosen, but \textbf{both ROC-AUC values are $\approx0.50$} (Figure~\ref{fig:model}a): neither model ranks up-days above down-days better than chance. The champion's high recall (0.922) merely reflects predicting ``up'' most days, exploiting the class prior. SHAP on the champion (Figure~\ref{fig:model}b) ranks recent risk (\texttt{volatility\_10}) and distance from trend (\texttt{sma\_ratio\_10}) highest, but all attributions are \textit{small}. This is the honest, expected outcome for price-only daily forecasting; its value is that the leak-free split, passing contracts, and small SHAP magnitudes together confirm the weak signal is \textit{real}, not a leak.

    \caption{The MLOps lifecycle in practice. (a) Data contracts gate the data before training. (b) Every run is tracked in MLflow; the champion is registered as \texttt{sp500\_direction\_model} (alias \texttt{candidate\_champion}). (c) Evidently flags dataset-level drift (4/8 features). (d) Hopsworks stores engineered features with lineage from Feature Group to training view. (e--f) The champion is served through a FastAPI REST API returning a class and probabilities.}
    \label{fig:mlops}
\end{figure}

\boldparagraph{Tracking \& registry.} Every run logs parameters, metrics, tags (\texttt{split\_strategy = chronological\_70\_15\_15}), the feature list, the model signature, and the serialised artifact to MLflow. The champion is registered as \texttt{sp500\_direction\_model} and loaded for serving by the stable alias \texttt{candidate\_champion}, so a newly promoted model is picked up without code changes.

\boldparagraph{Monitoring.} Evidently compares the oldest 70\% (reference) against the newest 30\% (current) with a normalised Wasserstein distance (threshold 0.1) and flags dataset-level drift: the non-stationary moving averages \texttt{sma\_10}/\texttt{sma\_20} drift heavily (scores $>6$) while the stationary return features do not, pinpointing exactly which features a production system should reformulate.

\boldparagraph{Feature store \& serving.} Engineered features are published to a Hopsworks offline feature store (Feature Group \texttt{sp500\_market\_features} v1 $\rightarrow$ training Feature View \texttt{sp500\_direction\_training\_view} v1) for reuse and lineage. The FastAPI service exposes \texttt{/health}, \texttt{/model-info}, and \texttt{/predict} (Pydantic-validated eight-feature input $\rightarrow$ class + probability) and is packaged as the Docker image \texttt{sp500-direction-api}. Reproducibility is structural: catalog-declared datasets, versioned \texttt{conf/} parameters, fixed random states, and a 125-test pytest suite plus the data contracts give two independent safety nets.

\section{From Proof of Concept to Production}

This PoC runs locally (Pandas in-memory, local MLflow with a SQLite backend, \texttt{yfinance} ingestion), but the technology choices are production-aligned, so deployment is incremental rather than a rewrite. \textbf{Advantages of the stack:} Kedro maps cleanly onto an orchestrator (Airflow/Kubeflow); MLflow already provides lineage, versioning, and a registry the API loads by alias; Great Expectations and Evidently make data quality and drift CI-friendly; Hopsworks gives feature reuse and train/serve parity; FastAPI + Docker yield a portable, scalable service; pytest plus contracts give two safety nets. Table~\ref{tab:risks} lists the main limitations with effort-scoped mitigations.

\vspace{-3pt}
\begin{table}[H]
\centering\small
\caption{Production risks and proposed mitigations (effort as additional sprints).}
\label{tab:risks}
\begin{tabularx}{\textwidth}{p{3.4cm}Xc}
\toprule
\textbf{Risk / limitation} & \textbf{Proposed mitigation} & \textbf{Effort} \\
\midrule
Pandas is single-node; will not scale to large/intraday data & Port feature/cleaning nodes to Spark (Kedro keeps the same node interface) & +3 wk \\
Local MLflow (SQLite + file store) is not multi-user or durable & Managed tracking server + cloud artifact store (S3/Postgres backend) & +1 wk \\
Hopsworks feature store is offline-only (no low-latency serving) & Enable Hopsworks online feature serving for real-time inference parity & +2 wk \\
\texttt{yfinance} is an unofficial, rate-limited source & Scheduled ingestion via a licensed vendor + retries/back-off & +1 wk \\
Drift is detected but retraining is manual & CI/CD with drift-triggered automated retraining \& promotion gates & +2 wk \\
Weak signal (ROC-AUC $\approx$ 0.50) & Add alternative data (macro, sentiment, cross-asset), calibrate, walk-forward backtest & +3 wk \\
API has no auth / observability & Add auth, rate limiting, logging, metrics (Prometheus/Grafana) & +1 wk \\
\bottomrule
\end{tabularx}
\end{table}
